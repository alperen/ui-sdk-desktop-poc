Original two-build baseline

This earlier session measured UI SDK and Plain React. Plain React had shorter total React render time and input processing time in every round at both sizes. At 100 items the render medians were 31.46 and 13.30 ms, a 57.7% reduction. Input processing took 62.15 and 35.62 ms respectively. All rounds and interaction tables.

Memoization

At 100 items the SDK recorded 8,539 hits across 10,418 useMemo calls (82%). The 1,879 factory executions took 0.270 ms within 2.050 ms total hook time. Its 9,073 useCallback calls had 7,539 hits and took 1.460 ms. Plain React recorded zero useMemo calls and 14 useCallback calls with 12 hits in approximately 0.015 ms. Neither implementation invoked a React.memo prop comparator. Diagnostic data.

HandleScope, FileListItem and ContextTriggerPart made 1,290, 1,266 and 1,257 useMemo calls respectively. The diagnostic clock advanced in roughly 5 µs increments. Across 50,000 empty timing brackets, average overhead was approximately 0.07 µs per bracket at 100 items. These timings cannot isolate net time saved or memory attributable to memoization. useMemo · memo.

Experimental setup

Headless Chromium 158, agent-browser 0.43.0, React and React DOM 19.3.1 and UI SDK 0.1.0-beta.5 ran sequentially on one machine at 1000 × 700 with CPU throttling off. The original fixture had 18 entries, including four children in Photos. Adding the same 96 files to both builds increased those counts to 114 and 100. Both applications used their own entry points, icons, styles and agent setup.

Each application and size received one warm-up for timing, diagnostics and traces. Each measured sequence started on a fresh page. UI SDK ran first in odd rounds and Plain React in even rounds. Each heap sample used a fresh Chromium process. Real keyboard and pointer inputs exercised desktop selection, marquee, drag, menu, folder opening and selection, rename, grid, columns, five nested folders, maximize/restore and close. Every sequence passed 26 state checks.

The functional suite ran five times. Each run passed 294 browser tests (147 per implementation) in 18 files and two Node tests. The fifth ran through pnpm validate. Suite wall time was excluded from render timings. Test output.

Reading the measurements

  1. The production profiling build used react-dom/profiling and a single root Profiler. We summed actualDuration across commits for each interaction. Initial mount was reported separately. baseDuration estimates the cost of rendering the entire subtree. React Profiler · Performance tracks · Commit records.
  2. A separate diagnostic build preserved component names. agent-browser recorded fiber activity. Instrumentation counted function entries and time in component bodies, including hooks and excluding child component bodies. Separate counters covered memo factories, hooks, callback hits and comparators. In the CSV, desktop_mount_calls covers initial mount and the other columns cover interactions. agent-browser React tools.
  3. Production traces measured the union of relevant EventDispatch intervals on the renderer main thread. Rendering combines UpdateLayoutTree, Layout, PrePaint and Paint. Nested intervals count once per category. The categories can overlap. GPU and compositor work are outside the scope. The shared traces contain selected events with relative timestamps from round three at 100 items. Decompress before importing into Chrome DevTools. SDK trace · React trace · Profiler.
  4. Heap usage was read after two garbage collection passes on the desktop, with the folder open and after closing. The opening metric spans the double-click to a task queued after the first animation frame with the rows laid out. It measures a paint opportunity, rather than physical presentation or field INP. Heap and opening times · Chrome memory tools.

Reproduce the baseline

From the project root, serve three benchmark builds in one terminal.

node benchmarks/serve.mjs

Record and summarize samples in a second terminal.

node benchmarks/run.mjs /tmp/desktop-perf-results
node benchmarks/summarize.mjs /tmp/desktop-perf-results

Results cover these two datasets and this desktop sequence. Mobile devices, other browsers, long-term heap behavior and the full SDK feature set require separate experiments.
